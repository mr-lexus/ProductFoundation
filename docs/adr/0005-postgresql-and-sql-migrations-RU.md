# ADR 0005: PostgreSQL и SQL-миграции

[English version](./0005-postgresql-and-sql-migrations.md)

- Статус: принято
- Дата: 2026-07-12

## Контекст

Бэкенду нужны надёжные транзакции, при необходимости — репозитории с изоляцией
арендаторов, идемпотентность и транзакционный outbox. Характер запросов продукта
пока неизвестен, поэтому выбор ORM сейчас закрепил бы неподтверждённые предположения.

## Решение

- PostgreSQL — основное хранилище достоверных данных.
- Единственный драйвер базы — `pg`; он изолирован в
  `@product-foundation/backend-postgres`.
- Прикладной код зависит от интерфейсов `SqlExecutor`, `TransactionRunner`
  и `TenantTransactionRunner`.
- История схемы основы — упорядоченный набор неизменяемых SQL-файлов
  в `packages/backend-postgres/migrations`. История продукта находится
  в готовом каталоге `apps/api/migrations` со своим пространством имён.
- Исполнитель миграций использует одну рекомендательную блокировку PostgreSQL,
  записывает SHA-256 и отклоняет изменения уже применённых миграций.
- Миграции выполняются отдельным разовым шагом до запуска API и фонового процесса.
- Рабочие миграции следуют expand/contract; down-миграции не служат обычным откатом.
- Конструктор запросов можно добавить за реализациями репозиториев позже,
  когда реальная сложность запросов будет измерена.

## Последствия

Начальный набор инструментов невелик, а SQL доступен для ревью. Транзакция
использует одно выделенное соединение с явной фиксацией, откатом и освобождением.
Команда должна тщательно проверять SQL и писать преобразование данных
для конкретных репозиториев. Будущее добавление ORM допустимо как решение
инфраструктуры, без изменения контрактов domain и application.

## Отклонённые варианты

- Изменение схемы при запуске приложения: небезопасно для управляемого развёртывания.
- Автозапуск миграций в каждой реплике API: связывает запуск реплик и размывает
  ответственность за развёртывание.
- Выбор ORM до появления репозиториев продукта: преждевременная привязка.
