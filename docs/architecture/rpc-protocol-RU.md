# Версионированный RPC на основе контрактов

[English version](./rpc-protocol.md)

## Решение

Публичная граница API определяется в `packages/contracts`. NestJS отвечает
за сборку приложения, Fastify — за обработку HTTP; ни один из них не служит
источником типов для фронтенда. Так сохраняется направление зависимостей:

```txt
packages/contracts
   ↑             ↑
apps/api    packages/frontend-app
```

Общий фронтенд никогда не импортирует `AppType` или другие типы реализации
из `apps/api`.

## Контракт процедуры

У каждой процедуры есть:

- постоянный идентификатор вида `module.action`;
- `kind: query | mutation`;
- версионированный путь `/rpc/v1/...`;
- схема входа Zod;
- схема выхода Zod, содержащая только публичный DTO.

Схемы описывают значения, передаваемые в JSON. Проверка во время выполнения
отклоняет `Date`, `BigInt`, экземпляры классов, циклические объекты
и преобразования, меняющие значение при повторном разборе. Нормализация
допустима, только если результат стабилен после сериализации в JSON
и обратного разбора.

Пока все вызовы используют HTTP-метод `POST`. Это упрощает одинаковую работу
клиентов Web, Capacitor и Tauri. HTTP-кеширование тяжёлых моделей чтения требует
отдельного решения и не прячется внутри RPC.

## Успешный ответ

```json
{
  "ok": true,
  "data": {
    "message": "Foundation is ready."
  },
  "meta": {
    "requestId": "01...",
    "servedAt": "2026-07-11T12:00:00.000Z"
  }
}
```

Поле `data` проверяется схемой выхода процедуры. Метаданные `meta` принадлежат
протоколу и не смешиваются с DTO сущностей и прикладных сценариев.

## Ответ с ошибкой

```json
{
  "ok": false,
  "error": {
    "code": "BAD_REQUEST",
    "message": "RPC input validation failed.",
    "retryable": false,
    "details": []
  },
  "meta": {
    "requestId": "01..."
  }
}
```

Публичные коды: `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`,
`CONFLICT`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `RATE_LIMITED`,
`INTERNAL_ERROR`.

Код domain/application не определяет HTTP-статусы. Ожидаемый отказ преобразуется
в `RpcApplicationError` на границе application/transport. Неизвестная ошибка
записывается в лог с идентификатором запроса, а клиент получает безопасный
`INTERNAL_ERROR`. Стек вызовов, SQL и внутренние сообщения не раскрываются.

## Контекст запроса

Обработчик получает:

- `requestId`;
- проверенный `idempotencyKey` либо `null`;
- время приёма запроса;
- `AbortSignal`;
- сведения об инициаторе (`kind`, `subjectId`) либо `null`, пока не добавлена аутентификация.

Обработчик мутации также получает явный `context.execution.transaction`.
Обработчик запроса на чтение получает обычный транспортный контекст без доступа
к транзакции базы данных.

После добавления аутентификации транспорт формирует сведения об инициаторе,
а прикладной сценарий проверяет его права. Репозитории не читают HTTP-заголовки,
контекст выполнения Nest или запрос Fastify.

## Отмена и повторные попытки

TanStack Query передаёт `signal` в RPC-клиент, затем в `fetch` и обработчик.
Отмена не означает откат серверной операции: для атомарности сценарию всё равно
нужна транзакция.

Автоматические повторы допустимы только для запросов на чтение и идемпотентных
мутаций. Каждая мутация требует `x-idempotency-key` и исполнитель, обеспечивающий
надёжную идемпотентность. Обработчик получает доступ к транзакции через
`context.execution.transaction`. Состояние продукта, сообщения outbox,
проверенный схемой ответ и завершённая запись идемпотентности фиксируются
одной транзакцией PostgreSQL. Ошибка откатывает их вместе. Повтор с теми же
данными возвращает сохранённый результат.

Внешние действия не выполняются внутри транзакции мутации. Мутация записывает
событие outbox, а идемпотентный обработчик фонового процесса выполняет действие.

Синхронная мутация должна держать транзакцию как можно короче. Конкурирующий
дубликат отклоняется неблокирующей рекомендательной блокировкой на время
транзакции. Длительные операции записываются в outbox и продолжаются в фоновом
процессе со своей политикой повторов и временного владения заданием.

## Версионирование

Внутри `v1` разрешены совместимые изменения:

- новое необязательное поле входа;
- новое поле выхода, которое старый клиент игнорирует;
- новый код ошибки — только после обновления базового пакета контрактов.

Удаление или переименование поля, изменение его смысла либо обязательности
требует `v2` или поэтапной миграции. Старую версию удаляют после подтверждённого
окончания периода поддержки.

## Добавление процедуры

1. Создайте схемы и контракт в `packages/contracts`.
2. Создайте или расширьте серверный модуль, отвечающий за эту функцию.
3. Реализуйте правило предметной области и прикладной сценарий.
4. Создайте тонкий обработчик в `modules/*/transport`.
5. Зарегистрируйте Nest-модуль в `apps/api/src/app/app.module.ts`.
6. Добавьте обёртку в `shared/api` и запрос или мутацию в соответствующий слайс.
7. Добавьте тесты успеха, проверки входных данных и ожидаемых ошибок.
8. Запустите `pnpm check`.

Пакетные вызовы, потоковая передача, загрузка файлов и подписки не добавляются
в общий адаптер заранее. Для них нужны отдельные транспортные возможности и ADR.
