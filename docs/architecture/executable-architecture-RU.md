# Автоматическая проверка архитектуры

[English version](./executable-architecture.md)

Документы объясняют замысел архитектуры, а `pnpm check:architecture` проверяет
важные границы ответственности и зависимостей независимо от автора изменения.
Основной код находится в [scripts/check-architecture.mjs](../../scripts/check-architecture.mjs),
правила платформ — в [scripts/frontend-boundaries.mjs](../../scripts/frontend-boundaries.mjs),
регрессионные тесты — в [scripts/check-architecture.test.mjs](../../scripts/check-architecture.test.mjs).

## Границы фронтенда

Проверка отклоняет:

- зависимости вверх по цепочке `app → pages → widgets → features → entities → shared`;
- импорт внутренних файлов другого слайса в обход публичного `index.ts`;
- зависимости общего фронтенда от API и платформенных оболочек;
- Capacitor вне Mobile, Tauri вне Desktop, код PWA и service worker вне Web;
- `import.meta.env` в `packages/frontend-app`;
- прямой `fetch` вне `shared/api`;
- относительные импорты между оболочками и зависимости одной оболочки от другой в манифестах.

Импорты разбираются через AST TypeScript: учитываются статические и динамические
импорты, реэкспорты, `require` и импорты типов. Проверка FSD одинаково обрабатывает
относительные пути, привычные псевдонимы `@/...` и глубокие импорты собственного
пакета `@app/frontend-app/...`. В общем фронтенде намеренно нет псевдонимов путей
TypeScript: проверка запрещает их, чтобы её разрешение путей не расходилось
с компилятором. Если псевдоним понадобится, вместе с конфигурацией необходимо
обновить разрешение путей и регрессионные тесты.

## Границы бэкенда и пакетов

Проверка отклоняет:

- импорты из `@product-foundation/*` в `@app/*`;
- импорты конкретных приложений из пакетов;
- NestJS/Fastify вне сборки API и транспортного слоя модулей;
- `pg` вне `backend-postgres`;
- зависимости от фреймворков и драйверов в `backend-core`;
- зависимости бэкенда из shared/modules вверх, в код сборки приложения;
- зависимости модуля из domain/application вверх, в infrastructure/transport;
- импорт внутренних файлов соседнего модуля;
- относительные импорты через границу пакета;
- циклы зависимостей и пространства имён пакетов, не соответствующие их роли.

Другие проверки охватывают чистоту репозитория, ссылки Markdown, безопасность
нативных оболочек, независимость сборок фронтенда, PWA, миграции, интеграцию
с PostgreSQL, переименование продукта и запуск через Compose. Полный список —
в [карте проверок](./foundation-readiness-RU.md).

## Пределы гарантий

Автоматические проверки не доказывают правильность поведения продукта, правил
авторизации, смысла SQL или сгенерированного кода. Они проверяют формальные
ограничения, которые можно надёжно установить по исходникам, манифестам и тестам.
Для нового важного правила сначала нужен конкретный сценарий сбоя, затем —
минимальная проверка и регрессионный тест. Расширять архитектурный линтер ради
гипотетической полноты не следует.
