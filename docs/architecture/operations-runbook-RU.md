# Инструкция по эксплуатации

[English version](./operations-runbook.md)

## Порядок развёртывания

1. Проверьте CI, свежесть резервной копии и результат последнего теста восстановления.
2. Соберите один неизменяемый образ для миграций, API и фонового процесса.
   Задание миграции получает `MIGRATION_DATABASE_URL`; API и фоновый процесс —
   только `DATABASE_URL` с минимальными правами. Рабочая роль tenant-режима
   должна иметь `NOSUPERUSER` и `NOBYPASSRLS`.
3. Один раз запустите `node dist/app/database/migrate.js`. Миграции основы
   используют пространство имён журнала `foundation`; каждый набор миграций
   продукта — отдельное постоянное пространство имён.
4. Разверните реплики API и проверьте `/health/live`, `/health/ready`,
   ошибки RPC и `/metrics`.
5. Разверните фоновые процессы и проверьте `:9464/health/ready`
   и `:9464/metrics`. Посмотрите число ожидающих сообщений, возраст самого
   старого, ошибки и сообщения с исчерпанными попытками.
6. Выполните проверочный запрос в рабочем окружении без чувствительных данных.

Во время развёртывания миграции должны быть совместимы и со старой, и с новой
версией приложения.

Миграции основы `0003_atomic_idempotency.sql` и `0004_outbox_claim_tokens.sql`
— явно оговорённые исключения для обновления бета-версий: остановите старые
процессы API и обработки, выполните миграции, затем разверните новую версию.
Применять их при постепенном обновлении работающих реплик нельзя. После
стабильного выпуска исключения потребуют отдельного ADR и согласованного окна
обслуживания. Обычные миграции остаются совместимыми по схеме expand/contract:
сначала расширение, затем удаление устаревшего.

Имена файлов миграций должны быть уникальны только в своём пространстве имён.
Не используйте одно пространство имён для разных продуктов и не меняйте
контрольную сумму применённой миграции.

## Откат приложения

### Доставка Web/PWA

Публикуйте `apps/web/dist` в корне сайта по HTTPS. Для `index.html`, `sw.js`
и `manifest.webmanifest` настройте повторную проверку актуальности кеша.
Длительное неизменяемое кеширование используйте только для файлов с хешем
в имени. Развёртывайте атомарно и сохраняйте старые файлы с хешами на время
обновления, чтобы открытые страницы могли догрузить свою версию.

Service worker предварительно кеширует только оболочку и статические ресурсы.
Его `NavigationRoute` обрабатывает переходы между документами, исключая ресурсы
и пути `rpc`, `health`, `metrics`. Настройте SPA-подстановку на сервере так же:
запросы к сервисам и ресурсам не должны превращаться в HTML. Без сети данные
API остаются недоступны.

Обновление предлагает «Перезагрузить / Позже». Отдельного таймера опроса нет.
Если отложить обновление, текущая страница продолжит работать; после закрытия
всех старых вкладок действуют обычные правила жизненного цикла service worker.
Ошибка регистрации не мешает пользоваться приложением.

Для отката опубликуйте предыдущую полную сборку, включая service worker,
в том же корне и области действия. Установка worker и согласие пользователя
происходят асинхронно: открытые страницы не меняют версию мгновенно. Для
аварийного удаления нужен специально подготовленный worker очистки по тому же
URL. Простого удаления `sw.js` или очистки чужих данных браузера недостаточно.
Проверка обновления между двумя сборками, подпись, интерфейс установки браузера
и правила работы продуктовых данных без сети не входят в smoke-набор.

Размещение в подкаталоге требует согласованных настроек Vite base, идентификатора,
области действия и стартового URL манифеста, а также навигации worker.
Заранее универсальной системы конфигурации для этого в шаблоне нет.

### Откат API и фонового процесса

Верните предыдущий образ API и фонового процесса. Не редактируйте применённые
миграции и не запускайте автоматически разрушительные down-миграции.
Добавленные столбцы и таблицы остаются до последующей миграции удаления,
когда все старые версии уже остановлены.

Если миграция завершилась ошибкой, её транзакция откатывается, а развёртывание
останавливается. Если когда-либо понадобится нетранзакционная операция
PostgreSQL, её ADR и ручной порядок восстановления должны пройти ревью
до слияния.

## Резервное копирование и восстановление

Рабочая PostgreSQL должна иметь зашифрованные автоматические резервные копии
и восстановление на момент времени. Не реже раза в квартал:

1. восстановите последнюю копию в изолированной учётной записи и сети;
2. примените миграции до развёрнутой версии;
3. проверьте целостность данных и основные сценарии приложения;
4. запишите фактические RPO/RTO и проваленные проверки;
5. удалите изолированное окружение по политике хранения.

Копия не считается проверенной до успешного восстановления. Локальные данные
Compose можно пересоздать; это не стратегия резервного копирования.

## Разбор инцидентов

- API недоступен, база исправна: проверьте структурированные логи запуска
  и ошибок, образ и конфигурацию.
- Readiness не проходит: проверьте соединение с PostgreSQL и загрузку пула.
  Сама проверка liveness при этом должна оставаться успешной.
- Растёт задержка outbox: не добавляйте реплики вслепую; проверьте частоту ошибок
  обработчиков, блокировки и доступность внешних систем.
- Есть сообщения с исчерпанными попытками: сохраните строки в пределах срока
  хранения, исправьте идемпотентный обработчик, проверьте сводные показатели
  и повторите одно проверенное сообщение. Не меняйте его содержимое на месте.
- Подозрение на утечку между арендаторами: отключите затронутую процедуру,
  сохраните журналы и доказательства, замените раскрытые учётные данные
  и запустите процесс реагирования на инцидент безопасности.

## Начальные ориентиры качества

До реального трафика это ориентиры для обсуждения, а не договорные SLO:

- доступность API: 99,9% в месяц;
- задержка RPC на 95-м процентиле: менее 300 мс, кроме заведомо длительных операций;
- доля серверных ошибок: менее 0,5%;
- возраст самого старого ожидающего сообщения outbox: менее 60 секунд;
- ни одного неустранённого нарушения tenant-изоляции при `DATA_SCOPE_MODE=tenant`.

Оповещения должны указывать ответственного и ссылаться сюда или на более
конкретную инструкцию.

## Просмотр и повтор необработанных сообщений

Административная команда показывает только сводные количества. Повтор требует
точного UUID сообщения и явного флага подтверждения:

```bash
DATABASE_URL=postgresql://... pnpm outbox:inspect:dev
DATABASE_URL=postgresql://... pnpm outbox:replay:dev -- <message-uuid> --confirm
```

Убедитесь, что исправленный идемпотентный обработчик уже развёрнут. Запишите
ссылку на инцидент или изменение, повторите одно сообщение и проверьте число
необработанных сообщений, частоту ошибок и внешние последствия, прежде чем
продолжать.

## Скрипты сборки зависимостей

В `pnpm-workspace.yaml` скрипты сборки зависимостей запрещены по умолчанию.
`esbuild` разрешён явно, поскольку инструментам нужен его платформенный
исполняемый файл. Необязательные скрипты `@parcel/watcher` явно запрещены.
Пакеты рабочего пространства подключаются через механизм injection, чтобы
современный `pnpm deploy` создавал переносимый образ API. Любое новое разрешение
на запуск скрипта требует проверки зависимости.
