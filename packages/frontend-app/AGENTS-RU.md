# Правила разработки с ИИ — общее приложение фронтенда

[English version](./AGENTS.md)

## Назначение

Файл определяет архитектуру общего фронтенда в `packages/frontend-app`.

Пакет содержит интерфейс и поведение продукта для:

- Web;
- оболочек Capacitor на iOS и Android;
- настольной оболочки Tauri.

Запуск платформы принадлежит оболочкам приложений. Логика продукта — этому пакету.

## Технологии

- React.
- TypeScript в строгом режиме.
- Инструменты фронтенда, совместимые с Vite.
- TanStack Query.
- Zod.
- SCSS.

React Router и Zustand — необязательные зависимости продукта. Добавляйте их,
только когда нужны маршрутизация или общее клиентское состояние.
Основа не устанавливает неиспользуемые слои состояния.

## Основные принципы

Предпочитайте:

- ясность — лишним абстракциям;
- единообразие — избыточной гибкости;
- явное поведение — скрытой магии;
- сопровождаемость — хитроумным решениям;
- композицию — наследованию.

Обычно выбирайте самое простое корректное решение.

## Структура исходников

Фронтенд следует облегчённой структуре Feature-Sliced Design:

```txt
src/
  app/
  pages/
  widgets/
  features/
  entities/
  shared/
```

Направление зависимостей:

```txt
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Импорты направлены только вниз. Можно импортировать любой нижний слой,
не только соседний:

- `pages` может импортировать `widgets`, `features`, `entities` и `shared`;
- `features` — `entities` и `shared`;
- `entities` — `shared`;
- обратные импорты запрещены.

Соседние слайсы одного слоя не зависят от внутреннего устройства друг друга.
Импорты между слайсами используют только публичные интерфейсы.
Циклические зависимости запрещены.

## Ответственность слоёв

### app

Содержит запуск приложения, маршрутизатор, провайдеры, макеты
и общую конфигурацию фронтенда. Не содержит бизнес-логику.

### pages

Содержит сборку маршрутов и страниц. Не содержит прямых вызовов API
и логики предметной области.

### widgets

Содержит переиспользуемые блоки страниц, таблицы, панели фильтров,
дашборды и разделы страниц. Собирает features и entities,
но не владеет бизнес-правилами.

### features

Содержит действия пользователя, сценарии и взаимодействия.

Примеры:

```txt
create-document
invite-member
update-profile
manage-subscription
```

Может использовать entities и shared.

### entities

Содержит предметные области, например:

```txt
user
organization
document
subscription
```

Определяет бизнес-смысл, но не экраны.

### shared

Содержит переиспользуемую инфраструктуру:

```txt
ui
api
lib
config
types
constants
```

Бизнес-логика здесь запрещена.

## Платформы

Пакет ориентирован на возможности платформ, а не на устройство оболочек.
Не помещайте связующий код Capacitor или Tauri в произвольные features.

Разрешены:

- абстракции возможностей платформы;
- использование стабильных адаптеров на уровне функции продукта;
- запасной вариант интерфейса, если возможность недоступна.

Предпочтительные места:

```txt
shared/lib/platform
shared/config/platform
```

Оболочки передают только конкретные зависимости с существующими потребителями.
Fetch подключается к API-клиенту или провайдеру при запуске. Не создавайте
общий контекст среды, локатор сервисов или реестр будущих возможностей.
Новые возможности добавляются отдельными явными интерфейсами по необходимости.
Импорты Capacitor, Tauri, PWA и `import.meta.env` принадлежат оболочкам.

## Публичные интерфейсы

У каждого слайса должен быть публичный интерфейс.

Пример:

```txt
entities/task/
  api/
  model/
  ui/
  index.ts
```

Разрешено:

```ts
import { TaskCard } from '../../../entities/task'
```

Запрещено:

```ts
import { TaskCard } from '../../../entities/task/ui/task-card'
```

Между слайсами используйте только публичные интерфейсы.
В пакете намеренно нет псевдонимов путей TypeScript: разрешение компилятора
не должно расходиться с архитектурной проверкой. Если псевдоним понадобится,
в том же изменении добавьте его разрешение и регрессионные тесты в инструменты
проверки архитектуры.

## Реэкспорты

Разрешены:

```txt
entities/task/index.ts
features/auth/index.ts
```

Запрещены вложенные файлы общих реэкспортов, цепочки реэкспортов
и деревья экспортов через `*`. Не допускайте циклических зависимостей.

## Архитектура интерфейса

Сторонние UI-библиотеки не используются напрямую в бизнес-коде.
Доступ ко всем UI-компонентам идёт через:

```txt
src/shared/ui
```

Бизнес-слои не должны напрямую зависеть от стороннего UI-kit.

## Управление состоянием

### TanStack Query

TanStack Query — единственный источник серверного состояния.

Правила:

- не хранить серверное состояние в Zustand;
- не дублировать кеш;
- не кешировать запросы вручную;
- не размещать fetch-логику в компонентах.

### Zustand

Zustand используется только для клиентского состояния.

Разрешены:

- состояние сессии;
- состояние интерфейса;
- предпочтения пользователя;
- многошаговые формы;
- временные черновики.

Запрещены:

- серверные коллекции;
- ответы API;
- дублирование кеша запросов.

Сначала используйте локальное состояние React. Переносите состояние
в Zustand, только когда оно общее, долговременное или относится
к отдельному многошаговому сценарию.

## API

Обращения к API централизованы.

Общая инфраструктура:

```txt
src/shared/api/
  client/
  queryKeys/
  types/
```

Entities могут определять только тонкие обёртки TanStack Query над общей
инфраструктурой API. Все HTTP-запросы и транспортная логика остаются
в `shared/api`. Entities не содержат прямой fetch и координацию бизнес-сценариев.

Используйте типизированные запросы и ответы. Интерфейс не должен зависеть
от нестабильных серверных контрактов.

Предпочтительный путь:

```txt
DTO
 ↓
преобразование
 ↓
модель предметной области
 ↓
интерфейс
```

Преобразование нужно, только если DTO отличается от модели интерфейса,
нужна нормализация или бизнес-преобразование. Простые DTO можно использовать
напрямую. Не создавайте бессмысленные преобразователи.

Не зашивайте смысл продукта и правила сценариев в компоненты.
Общие с бэкендом контракты импортируйте из `packages/contracts`,
а не дублируйте локально.

## Формы

Все формы используют Zod для проверки данных. Смешивание систем проверки
запрещено. Внутри каждой feature должна быть единая архитектура форм.

Состояние формы принадлежит feature, если оно не используется несколькими
features.

## Права доступа

Проверки ролей и прав централизованы. Код вида

```ts
if (user.role === 'admin')
```

запрещён в произвольных компонентах.

Используйте общие функции проверки прав в:

```txt
src/features/auth/permissions
```

Проверки должны переиспользоваться, тестироваться и не зависеть
от состояния интерфейса.

## Стили

Используйте SCSS и именование BEM.

Правила:

- каждый UI-блок имеет одно явное имя BEM;
- элементы: `block__element`;
- модификаторы: `block--modifier` и `block__element--modifier`;
- имена классов описывают структуру и состояние, а не догадки о внешнем виде;
- избегайте неструктурированного склеивания `className`, скрывающего состояния;
- избегайте глубокой вложенности селекторов, если можно добавить понятный BEM-класс;
- встроенные стили допустимы только для действительно динамических значений,
  которые нельзя выразить модификаторами или CSS-переменными.

BEM должен помогать чтению, а не превращаться в формальность.

## Списки и таблицы

Коллекции с одинаковой моделью взаимодействия должны иметь общее поведение.

Поддерживаемые возможности:

- постраничная загрузка;
- сортировка;
- фильтрация;
- массовые действия;
- выбор строк;
- видимость столбцов;
- группировка, когда она отражает понятия продукта: владельца, категорию или статус.

Логика коллекций должна переиспользоваться через хуки или модули features.
Не размещайте специальную логику таблиц и списков в pages.

## Производительность

Предпочитайте:

- постраничную загрузку на сервере;
- вычисляемое состояние рядом с использованием;
- мемоизацию только для реальной проблемы рендеринга;
- ленивую загрузку.

Избегайте:

- ненужного `useEffect`;
- широких подписок на контекст или хранилище, вызывающих лишний рендеринг;
- загрузки полных наборов данных;
- ненужного копирования состояния.

Ориентир — 200 строк за один рендер. Выше этого рассмотрите
постраничную загрузку или виртуализацию.

## Компоненты

Предпочитайте небольшие компоненты, узкую ответственность и композицию.
Выносите переиспользуемую логику интерфейса и взаимодействий в хуки.

Около 200 строк — повод оценить разделение компонента, а не жёсткий лимит.
Принимайте решение по содержанию.

## Хуки

Категории:

```txt
useUi*
use*Query
use*Mutation
use*Store
```

Хуки остаются средствами интерфейса и взаимодействий.

Используйте их для:

- подключения состояния интерфейса;
- композиции запросов и мутаций;
- переиспользуемых обработчиков взаимодействия;
- вычисляемого состояния конкретного представления.

Не используйте для:

- правил предметной области;
- бизнес-преобразований;
- координации бизнес-сценариев;
- скрытых сервисных слоёв.

Предметная логика принадлежит entities и features. Если логика отвечает
на бизнес-вопрос, поместите её туда, а из хука вызывайте.

Поведение коллекций и таблиц может находиться в хуках только как поведение
интерфейса. Смысл продукта и правила сценариев остаются в features или entities.

## Ответственность

У каждого файла должен быть понятный владелец. Размещайте логику на самом
высоком уровне, где ответственность остаётся ясной:

- shared — только инфраструктура;
- entities — логика предметной области;
- features — прикладная логика;
- widgets — сборка интерфейса;
- pages — сборка маршрутов.

Не создавайте свалки утилит. Не переносите логику вниз без ясной причины.

## Проверка

Каждое нетривиальное изменение проверяется до завершения.

Минимум:

- полностью прочитать затронутые файлы при изменении архитектуры,
  общей инфраструктуры или публичных интерфейсов;
- выполнить доступную диагностику, линтинг или проверку типов затронутой области;
- запустить связанные тесты при изменении бизнес-логики, преобразований,
  прав, проверки данных или поведения запросов;
- явно указать, если проверку выполнить не удалось.

Не заявляйте об исправлении без результатов проверок.

## Архитектурные решения

Крупные решения документируются в `docs/adr`. Существенные исключения
и долгосрочные изменения архитектуры оформляются ADR.

Локальное исключение можно описать коротким комментарием рядом с кодом
или в `docs/architecture-exceptions.md`.

Каждое исключение указывает:

- от какого правила отступают;
- почему обычное правило здесь хуже;
- на какой участок распространяется исключение.

Выбирайте самый лёгкий формат, в котором исключение будет легко найти.
